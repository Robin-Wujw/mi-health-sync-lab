# Healthlab 19：只写变化的记录，缺细节的副本不再覆盖完整记录

版本：1.0.6-healthlab.19 / 1000025；沿用原包名和签名，可覆盖安装。

本版只改小米 → Health Connect（HC）方向的写入和同步失败范围。Zepp → HC → 小米的导入流程、账本和云端写入逻辑没有改动。

## HC 写入

.18 及之前，每次同步都给窗口内的所有记录分配新修订号，HC 因此全部重写。这带来两个问题：

- 读取 HC 的其他 App 看到所有记录都被修改，写入配额也花在没有变化的数据上。
- 缺细节的副本会覆盖完整记录。FDS 下载失败的运动会丢路线；跨越同步窗口起点的运动会丢掉一部分心率序列。

.19 的 `clientRecordVersion` 由两段组成：高位是原来的持久化修订号，低 20 位是记录内容的指纹。写入前读取本 App 自己已写的同类记录，再按下面的规则决定：

| 情况 | 处理 |
|---|---|
| HC 里没有这条记录（包括被删除） | 写入 |
| 新副本细节更多 | 写入 |
| 新副本细节更少 | 不写，保留 HC 里的完整记录 |
| 细节相同，内容没变 | 不写 |
| 细节相同，内容变了（包括数值变小） | 写入，修订号更高，所以新值生效 |
| HC 里是 .18 及之前写的记录，细节相同 | 写入一次，之后按指纹比较 |

“细节”的计算方式：心率、速度、步频、踏频和功率看样本数；运动看路线点数加备注项数；睡眠只区分有无阶段，因为修订时阶段可能合并。其他指标没有细节之分。

这条读取依据官方说明：只有写入权限的 App，在前台和后台都能读取自己写入的记录（`HealthConnectManager.readRecords`，API 34 起）。官方写入指南也要求每次同步只写新增和变化的数据。读取失败时，该类型按 .18 的方式全部写入，比较失败不会阻断同步。

## 同步失败范围

运动只把云端心率当作补充数据。.18 里心率读取失败会让运动一起失败，等待运动的步数、距离和卡路里也跟着失败。.19 只有心率本身失败。会话过期仍会触发刷新。运动读取失败时，步数、距离和卡路里继续报错，因为无法扣除运动重叠。

## 手机上怎么确认

覆盖安装后同步两次，用下面的命令看日志。日志只有记录类型和数量，没有健康数值：

```powershell
adb logcat -s HealthRecordChange
```

- 第一次同步：旧记录会各重写一次，`to write` 接近 `candidate(s)`。
- 第二次同步：没有新数据时，`to write` 应该接近 0，例如 `HeartRateRecord: 288 candidate(s), 288 stored, 2 to write`。
- 如果出现 `could not compare with stored records`，说明这台设备不允许读取，该类型退回全部写入。这不影响同步，但本版的改进在这台设备上不生效。

## 已知限制

- 指纹只有 20 位。内容变化时约有百万分之一的概率指纹相同，这次修正会被跳过，直到内容再次变化。
- 云端如果真的删掉了某个样本，样本更少的新副本不会覆盖旧记录。这是“缺细节不覆盖”的代价。
- 降级到 .18 后，它写入的版本号低于 .19 已写的记录，HC 会忽略这些写入。

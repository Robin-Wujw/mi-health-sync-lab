# Healthlab 14：心率待确认恢复与操作入口合并

版本：1.0.6-healthlab.14 / 1000020。沿用包名和签名，可直接覆盖安装。Google Health、Zepp 源时间戳及其日期归属逻辑未改。

## 使用

1. 覆盖安装 APK，保留登录、权限和导入记录。
2. 同步范围选 14 或 30 天以覆盖旧待确认心率；保持“心率 → 小米”开启。
3. 在同步页点击“处理未完成数据”。该操作会真实补传仍缺失、通过预检的记录；已存在的数据只核对。运行中显示每项已核对和剩余条数。
4. 完成后查看结果。遇到冲突、拒绝、来源变化、查询未完成或提交后未确认会停止；不要把接口受理或新版安装成功当作数据恢复成功。

每项一次最多处理 300 条，按时间顺序逐条提交，每条读回成功后再继续。未确认的同一目标保留已经消耗的恢复次数，后续点击不会越过它去继续提交，也不会自动重置额度。来源冲突仍需单独解决；恢复按钮不会把错误的源数据改成成功。

## 界面

- 原“核对全部待确认血氧”“恢复一条待确认血氧”合为“处理未完成数据”，处理已启用的心率和血氧。
- “查看结果”展开后才显示详细诊断和复制报告按钮。
- 设置里的单条测试、旧睡眠 HRV 补全、已确认睡眠修订收进“高级诊断与兼容选项”。原设置值和权限不变。
- 正常同步和显式恢复共享全局互斥锁，不能同时运行。

## 实现及验证

心率预检原生历史上限为 128 页，血氧仍为 32 页；只有明确结束的历史读取才允许缺失记录进入恢复。一个操作内共享提交前历史快照，每条保留临近提交的实时查询，提交后的读回不使用该快照。每条请求前持久化恢复保留记录，保存受理状态、业务码和读回状态；取消或重启不会自动重传。

心率使用精确时间和值核对，不套用血氧分钟取整。只允许同一来源和内容未变化的旧 pending；可定位到具体心率目标的源冲突只阻止对应目标；无法定位到目标时按日期保守判断，未知影响范围继续阻止。日报仍保留原来的完整日期保护。

683 项测试通过（composeApp 623、miclient 60）；主 APK 和测试 APK 构建成功。新增 8 项测试覆盖恢复顺序、历史复用、失败停止与重入、分页不完整、来源变化、非分钟别名、冲突日期隔离、实时墓碑拦截及处理上限。

2026-11-04 重连后已覆盖安装最终主 APK 和测试 APK。30 天只读恢复预检完成：当前 349 个待确认候选（较前次调查增加 49），最早目标来源未变、查询缺失；118 页原生历史明确结束，eligible=true，已经走到提交前保留步骤。测试在此步骤主动返回，不修改本地日志、不上传健康数据。报告里的 RESERVATION_CHANGED 是只读测试刻意阻止保留操作的结果，不是生产恢复发生竞态。

该预检只证明最早目标可进入恢复，不代表全部 349 个已逐一通过，也不代表实际补传成功。一次最多 300 个；全部顺利后可以再处理剩余记录。主 APK 已安装；真实补传仍由用户在同步页显式点击。

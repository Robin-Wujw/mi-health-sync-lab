# Mi Health Sync Lab 1.0.6-healthlab.9

本版针对 .8 反馈中的血氧恢复验证和历史诊断缺口。用户已确认睡眠恢复正常，本版保留该流程。版本为 `1.0.6-healthlab.9 / 1000015`，包名与签名沿用 .8，可覆盖安装。

## 安装后操作

1. 覆盖安装主 APK，保留现有应用数据、登录和本地恢复账本。
2. 保持原来日期范围，点击 **“核对全部待确认血氧”**。
3. 复制本次诊断。重点查看 `pending_reconcile.oldest_previous_*`：这部分直接读取手机中已经保存的历史结果，不需要旧报告。

这次核对不上传健康数据。仅当读到明确匹配且本地状态未变化时，才更新对应的本地待确认状态；仍然缺失的记录继续保留。无需为了获取历史结果再点击单条恢复。

## 最新日志意味着什么

用户 .8 报告为 203 条来源、70 条已有匹配、133 条待确认。最近一次单条恢复为 `RETRY_ALREADY_CONSUMED`、本次上传 0 条、上次结果 `READBACK_UNVERIFIED`。这表示最早那条待确认记录已经使用过一次恢复机会，上次未能读回验证；不是本次服务端拒绝了上传，也不是 133 条都试过恢复。

完整原生历史查询已经结束仍未返回这 133 条，不能继续把当前问题仅归因于页数上限。`legacy_row_metadata_unknown=true` 表示早期 pending 账本没有保存完整外层时区，不代表恢复请求漏传时区。

## 本版修复

- 单条恢复上传后三次普通窗口查询未能验证时，新增一次原生历史读回，最多 32 页，不追加上传。明确匹配可以确认；不完整查询的缺失不冒充完整缺失。
- 同次上传后的来源、删除和内容冲突会保留，后续匹配或查询失败不会抹掉这些证据。上传后认证失效也不会触发整次操作重传。
- 从原有账本显示上次是否受理、业务码、读回分类及历史元数据完整性；未知仍显示未知。历史结果与本次请求分开。
- “核对全部待确认血氧”也附带当前范围最早待确认目标的已有恢复历史，方便零上传取得上次结果。不会跳过最早未解决目标去选其他记录。
- 通过读到已有记录解除待确认时，使用原子校验并更新，避免清掉并发变化的本地状态；读操作不冒充本应用上传归属。

现有已消耗额度不会重置。新版读回补充主要修复以后符合条件的单条恢复验证；它不能重做已经发生的上传，也不能保证这次 133 条能恢复。

## 新增报告字段

| 字段 | 含义 |
|---|---|
| `pending_reconcile.oldest_previous_outcome` | 最早待确认目标先前保存的恢复阶段结果 |
| `pending_reconcile.oldest_previous_accepted` | 上次接口是否表示受理，`unknown` 表示未保存明确结论 |
| `pending_reconcile.oldest_previous_business_code` | 已保存的上次业务码，未知不填 0 |
| `pending_reconcile.oldest_previous_readback_status` | 上次保存的读回分类，不能当作本次核对结果 |
| `pending_recovery.previous_*` | 单条恢复入口中的同类历史证据 |
| `pending_recovery.precheck_status` | 当前操作上传前的核对分类 |
| `pending_recovery.native_readback_*` | 当前上传后的原生读回页数、完整性、停止原因、分类与是否失败 |

`accepted=true` 只代表接口受理响应，仍需独立读回才能确认保存。所有新增字段只含布尔、数字或固定枚举，不输出账号、令牌、源记录 ID、精确时间、健康数值、完整请求响应。

## 验证范围

实际测试数量、签名和 APK 哈希见 `validation-healthlab9.json`。测试覆盖原生独立匹配、冲突不被后续读取覆盖、读取不完整/失败、历史受理信息、原子校验、额度和零上传核对。旧版文档与 validation 文件保留为历史记录。

本机没有连接 ADB 设备，没有访问用户账号或执行真实健康上传。手机端这 133 条的恢复、小米 App 展示尚未验证。iOS 未构建。

如使用配套电脑测试包，可执行以下只读云端核对：

```powershell
.\Invoke-MiHealthLiveTest.ps1 -Mode reconcile-pending -Metric spo2 -RangeDays 3
```

日期范围应与手机原操作一致。此入口可能更新已匹配记录的本地账本，健康上传为零。
